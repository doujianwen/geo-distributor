## 可以接受的边界

1. 隔离环境使用明确标记的虚拟数据与假提供方是合适的测试方法，不能推导真实采集或历史接入通过。
2. 受控单站点试用可以作为中间交付；项目和产品权限模型不能因此省略，更不能声称满足完整替代。
3. 保留现有站点总版本可防止覆盖，是保守过渡；并发编辑不同对象会冲突的限制必须可见，并记录对象版本后续验收状态。
4. 业务提示词与手工回填流程应保留；内部密钥、系统模板、重置和种子数据工具属于维护范围。不得一概以安全为由删掉业务提示词库。
5. 不应为了迁移形式直接开放原内部 API 或复制其全库读取。可以复用原组件/业务函数，按原操作语义增加严格的授权适配。
6. 实际优化人员走查属于人类验收，不能由本独立子代理或主代理扮演并签署。技术验收可以先完成；该门槛如仍缺，必须准确保留。

### 本轮确实发现并推动修复的实施问题

1. 个人票据校验使用 Python `assert`，优化模式可能删除 issuer/时间/主体检查。主实施者已改显式拒绝；独立子进程 `python -O` 反例现拒绝非法票据。
2. 分类应用直接信任浏览器提交的 drafts。现根据服务端已保存预览、主体、资源、版本、子集摘要核验；篡改草稿被拒绝。
3. 新 prepare 能力被原角色再次否决。已统一受保护命令的有效能力；客户 prepare-only 可准备问句，仍不能打开专业作业台。
4. 仅复核权人员无法看到待复核原文，导致职责分离不可实际操作。新增复核读取投影；可看 HOLD 来源，不能编辑问句，自录自审仍拒绝。
5. 已取消项目仍能走原生/整合两个路径写入。独立测试最初返回 200 并写入；现两条路径均拒绝，历史读取保留。
6. 新增多资源后，项目级能力会隐式覆盖新产品；按全部资源能力聚合又可能让“仅获第二资源授权者”省略 selector 后取得主资源权限。新增显式资源授权和默认授权资源选择后，独立负向测试通过。

以上为反馈闭环，不把主实施者修补过程称为独立实施。独立复验有真实失败记录：仅复核者看不到 HOLD 原文、取消项目仍写入均先失败后通过。测试夹具曾因演示种子目录名称不合法而启动失败，已修正到临时 `portal-demo`；副项目原为 BLOCKED，跨项目测试在临时库明确设为执行中后再绑定，未为使测试通过而放宽产品拒绝条件。
