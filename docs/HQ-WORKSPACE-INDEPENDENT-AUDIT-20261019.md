2026-10-19。审计者：独立子任务 `hq_independent_audit`。本轮是设计与既有实现对照审查，未以页面效果替代实施验收，未修改业务代码或真实数据。

## 结论

七个总部入口与既有对象、角色的映射合理；在下列条件明确纳入唯一执行指令后，可进入实现。当前结论是**设计有条件通过，实施待复验**。用户要求的独立审计并不意味着允许扩大为财务、人事、账号管理、客户密码或新的增长计算系统。

审查证据：`HQ-WORKSPACE-REVIEW-20261019.md`、`api/auth.py`、`api/deps.py`、`api/ui.py`、`api/request_workflow.py`、`api/customer_service.py`、`api/routers/leads.py`、`projects.py`、`requests.py`、`customer.py`、`geo_distributor/models/project.py` 和 `ui/app.js`。Notion 的增长核心历史门禁为文档引用背景，独立审计未将另一服务的历史认证缺陷推定到本服务，也未独立复述未读取的 Notion 原文。

## 范围和完整性检查

- 沿用现有 HQ_TECHNICAL/HQ_MANAGEMENT。技术角色可拟范围与运营交付，批准/拒绝按现有管理角色约束；不因“运营”文案新造权限组。发布能力按现有服务端规则保留，前端不能扩大。
- 启动、完成阶段、推进阶段、生成报告、向客户发布须以不同动词和事实呈现。完成四阶段不代表项目验收；不增加无依据的“已验收”操作。
- 旧项目深链、客户详情、GEO 数据、报告打印、需求补充应继续工作；聚合链接必须使总部能够到达正确资源，错误保留导航。
- 范围编辑、拒绝/补充说明、客户协作表单应统一 dirty guard；409 保留输入并要求刷新，不以自动刷新丢失编辑代替冲突处理。
- 视觉与键盘验收覆盖 1440、768、390 宽度；对每个总部导航至少一次正常读取、空状态和明确错误验证。截图或画面导出不能替代 API 权限、事务、幂等、持久化证据。

## 独立实现复验与定向闭环

复验读取 `api/hq_service.py`、`api/routers/hq.py`、原线索/需求/项目入口、状态仓储、总部会话别名及前端七个导航。SQLite 分配与项目操作均使用事务内读取/校验/写入；项目操作与事件同一事务，旧 start/stage/complete 入口调用同一实现。手工产出引用全部明确拒绝，原交付链路继续负责产出。总部聚合以现有发布指纹判断结果资格；撤回与失效、客户待答与团队待处理分别计数。会话取用重新检查凭据，HQ 使用独立 cookie；演示业务写屏障位于服务端。

独立复验发现并提出以下实现缺陷，主实施任务已定向修正：

| 编号 | 复现与影响 | 修正与证据 |
|---|---|---|
| IR01 P1 | UI 支持总部直管线索，但原转换 API 拒绝 HQ-INTAKE；初次放行后，已转换重放仍被状态前置检查拦截。 | 直管可建相同 ServiceRequest；已有 request_id 的重放优先返回；独立测试确认一客户、一需求、批准前无项目。 |
| IR02 P1 | 直管需求进入补充状态后没有渠道管理员身份可提交；总部也被禁止补充，受理永久停住。 | 仅 HQ-INTAKE 需求允许现有 HQ 补充；普通渠道需求仍仅渠道管理员。独立测试同时验证直管成功与普通渠道拒绝。 |
| IR03 P2 | 待分配统计包含 new 与 pending_assignment，卡片队列只显示后者，导致计数与下钻不一致。 | 卡片改用 unassigned 队列，预筛两状态。对照代码已确认，实际浏览器交由主任务验收。 |
| IR04 P2 | 进入带 queue 的列表时每次重置筛选/页码，返回详情会丢失用户调整。 | 列表状态改为按 section 与 queue 保存引用；前端源代码复核已确认，浏览器往返由主任务验证。 |
| IR05 P2 | 发布指纹有效但客户已停用，HQ 仍声称“客户当前可见”，而客户认证会拒绝访问。 | 增加 access_inactive 投影与“发布有效 · 客户访问已停用或档案缺失”标签；不把停用当来源失效，不改测量/发布核心。独立测试覆盖停用后结果状态、异常计数与客户 403。 |

新增 `tests/test_hq_independent_audit.py` 六个独立回归，覆盖上述直管流程、客户停用、旧新生命周期版本一致、同键并发事件唯一、全部旧入口拒绝三类手工产出编号。

独立执行测试记录：总部/独立/GEO/受理链组合 **79 项通过**（当次包含独立测试前五项）；客户与独立前四项组合 **45 项通过**。第一次客户组合碰到 Windows asyncio 创建内部 socketpair 的 `Unexpected peer connection`，未到业务断言；原失败用例在后一组合重跑通过。独立测试最初有一处调用仓储不存在的 `list_all`，已改为实际 `hq_service.all_rows` 后通过。未将这些中间失败隐去或认作业务功能通过。

最终独立六项加认证回归 **29 项通过**，包含客户停用发布状态与直管补充权限定向验证。上述组合合计覆盖 144 个不同测试，重复执行的独立用例不重复计数。

**独立实现复验结论：已发现的安全与业务一致性阻塞已关闭，本轮代码边界及相关回归通过。** 本审计不替代主任务的浏览器交互、运行进程及真实库前后指纹验收；这些证据由主任务另行归档。生产 BLOCKED 不变，不将本机代码复验提升为生产就绪裁决。

## 最终定向复核：演示重启边界

主任务在最终运行重启发现原演示数据库保护以 payload 中优先存在的 `client_id` 推断所有记录的主键，导致待分配线索因空 client_id 被误拒绝。独立复核确认 `scripts/portal_demo_data.py` 已按六张业务表明确选择各自的主键字段，不再把关联客户编号当对象主键；payload tenant 必须等于存储列 tenant，只有 leads_intake 允许 HQ-INTAKE，其他记录限 DEMO-GEO/DEMO-PARTNER，主键 payload 仍须 DEMO- 前缀，目录与文件符号链接防护仍保留。该修正使合法的总部待分配演示线索可重启读取，没有放开任意真实租户或真实对象编号。

独立仅重跑本次新增三项定向回归：演示重启八类队列 payload 不变与非演示项目编号拒绝、内存事务兼容、需求所选租户与资源冲突拒绝；结果 **3 项通过（2.70 秒）**。未无故重跑已通过的全套。代码/接口审计原通过结论保持；此新增证据不改变生产 BLOCKED。
