> 2026-10-20纠偏：面向所有角色统一六入口的设计未覆盖原内容增长系统15个页面及其专业操作，相关“覆盖通过”结论撤回。专业作业部分以 [V2.1专业作业纠偏方案](WORKSPACE-EXPERIENCE-REDESIGN-V2.1-OPERATOR-20261020.md) 为准。个人账号、总部开通、客户身份合并方向保留。本文件及原静态示意不再作为专业能力完整性的验收依据。

日期：2026-10-20，Asia/Shanghai。状态：**经三种角色视角的两轮方案审查后形成的修改建议，待确认；未开始实施。**

本轮仅新增方案和结构示意文件，未修改业务代码、账号权限、客户记录或增长核心规则。审计登录使用现有隔离演练身份；未提交业务修改。客户编辑越权批准证据的负向请求返回403。

## 1. 结论与审计口径

本次修改同时覆盖账号、信息架构、工作任务、数据表达和视觉系统。产品目标是：用户用自己的账号登录，系统自动进入其被授权的工作空间；先看到当前情况和需要处理的事情，再进入相应GEO功能。

统一保留四类业务身份：总部管理员、总部运营、渠道商管理员、客户成员。客户编辑/查看合并为一种客户身份与一个客户工作区，查看、补充资料、提建议和执行任务由后台能力授权决定。合并身份不意味着给所有客户相同写权限。

本轮“自辩、互辩、复审”由同一主审按产品设计、功能开发、客户三种视角结构化开展；不是三名真人访谈，也不冒称新增独立第三方审计。上一轮独立审计与205项回归证明的是原有实现的功能和权限，不等于本方案已经开发、用户体验已经验证。

设计P0表示：进入公开注册及真实账号试用前必须解决的方案缺口；不代表本轮已证明当前隔离演练发生数据泄露。

## 2. 现状实查与初审

已检查演练入口、总部概览、问题与内容、测量登记、客户概览和客户行动界面，并核对门户与WordPress桥接源码。

| 现状证据 | 用户影响 | 初审判断 |
|---|---|---|
| 登录前显示总部管理、运营、渠道商、客户编辑、客户查看5个按钮 | 需要先理解系统角色；不能建立自己的身份 | 当前是验收启动器，需要另做用户入口 |
| 总部左侧业务导航与内容区10个GEO横向入口并存 | 工作流、数据模块和功能入口分成两套认知结构 | 整合为一套主导航，业务流程放入对应工作场景 |
| “问题与内容”页有5组列表/搜索、10个折叠表单、合计37个输入控件；当前视口页面高3387px | 创建/修改、人群/场景/主题/内容挤在同页，重要操作难以定位 | 按对象分二级页，每次只处理一个对象 |
| 登记回答表单有21个字段、17个必填 | 要求运营理解模型、配置摘要、时区等技术细节 | 提供受控结果导入与预览；专业手工模式分步、预填可信上下文 |
| 客户行动卡片没有直接任务处理按钮 | 需另开表单，再选行动和目标状态 | 从具体任务直接操作，合法下一步由服务端返回 |
| 客户页仍显示“客户编辑”身份标签 | 用户把权限当成另一个产品入口 | 同一客户工作区，权限解释放到账户/团队信息 |
| 概览重点是对象数量和流程说明 | 客户不能快速回答“有什么变化、我该做什么” | 首页围绕结果、待办和下一步组织 |
| 手工填写target_context、SHA-256及对象状态等细节 | 对业务用户暴露内部实现 | 上下文与摘要从可信对象/采集记录取得，不要求普通用户维护 |
| `api/auth.py`主要是接入密钥，`growth_lab.py`是角色启动器 | 改成邮箱和密码两个框不能形成真实账号体系 | 身份链路是必须实施的功能工作包 |
| WordPress桥接将administrator/editor映射到两个租户，且自述仅用于验证 | 不能表达多人同企业、多客户授权，也不能把WP编辑权限等同总部运营 | 保留账号基础，新增明确的工作空间成员关系 |

本轮不以“没有横向溢出”作为界面友好的证明。结构、认知负担、主任务可发现性和错误恢复均需重新验收。

## 4. 第一版主张、自辩与互辩

以下先列主张，再保留反方质疑和最终取舍，避免把第一稿直接标为审计通过。

| 主张方与初稿 | 本方自辩 | 另一视角的挑战 | 补充后的决定 |
|---|---|---|---|
| 产品：移除角色按钮，统一登录 | 降低入口理解成本 | 开发：当前没有真正的用户注册审批链，不能只改登录外观 | 账号、成员归属和开通审批作为首要功能包 |
| 开发：先保留密钥，加一个友好的名字 | 可快速复用现有认证 | 客户：我的密码重置、账号停用和个人操作归属在哪里？ | 用户登录改用个人账号；集成密钥仅留服务端 |
| 客户：客户编辑/查看合并，按钮都给我 | 不再因身份分叉迷路 | 开发：查看报告的人不应默认能改品牌事实或执行任务 | 合并界面，保留按人/企业/项目/动作授权 |
| 产品：把十模块全放左侧 | 每个模块更容易看见 | 客户：入口多仍需学习；重复的内容与报告概念未解决 | 六个主要工作区，十模块映射到明确二级入口 |
| 开发：继续通用表单以便覆盖所有状态 | 实现简单、覆盖完整 | 客户：为什么开始任务还要重新选任务和状态？ | 任务卡直接操作；系统计算可用下一步，不让用户选择非法状态 |
| 产品：首页增加漂亮的趋势图 | 更像成熟SaaS | 开发：现有示例只有两个观测点，部分数据还未采集 | 两点显示前后对照；趋势需满足既有可比口径；缺数据明确说明 |
| 客户：希望能提交完成说明 | 不想只点“开始”后失去入口 | 开发：不能让客户直接把Action改为published/measured | 新增执行材料/反馈的持久记录，由总部复核，原Action状态不扩写 |
| 开发：把技术字段藏起来 | 表单更短 | 产品：缺少采集配置时不能用默认值冒充真实来源 | 导入预览显示缺项；不完整即阻断比较；专业模式仍可查看来源元数据 |
| 产品：保留匿名管理员一键演示 | 方便销售和验收 | 开发：未来公开后会变成无验证的高权限入口 | 用户仅有只读示例体验；可写演练使用真实测试账号，角色启动器仅维护环境保留 |
| 客户：首次登录就看到结果 | 容易理解价值 | 产品/开发：新项目未采集、账号待审核时不可能有真实结果 | 展示明确开通/采集步骤，提供独立示例项目，不伪造个人结果 |

## 5. 红队缺陷清单与定向修订

| 编号 | 优先级 | 挑战 | 必须落实的修订 |
|---|---|---|---|
| R01 | 设计P0 | 登录页换壳，内部仍是共享密钥冒充个人 | WordPress作为账号唯一真源；门户建立稳定个人主体，密钥不交给用户 |
| R02 | 设计P0 | 公共注册可选择总部管理员/运营 | 公开申请不赋予内部身份；内部人员由已有总部管理员配置 |

| R04 | 设计P0 | 将WP administrator/editor直接当产品身份 | CMS职责与平台能力分离；停用旧演示映射进入正式授权的路径 |
| R05 | 设计P0 | 同一“客户身份”使所有人获得写权限 | 个人成员能力和动作范围每请求校验；编辑与只读共享UI但授权各自独立 |

| R07 | P1 | 注册后只能看到空白或被反复弹回登录 | 可登录查看自己的开通申请、补充资料和处理结果；业务数据授权另行判断 |
| R08 | P1 | 账号开通审批与服务需求批准混为一件事 | 分开“开通权限”“确认服务范围”“批准优化行动”及其记录，不替换旧流程 |

| R10 | P1 | 客户的“已完成”直接变为交付验收 | 执行反馈单独记录；总部继续拥有发布/质量/复测确认，不新增假Action终态 |

| R13 | P1 | 同名/相同邮箱的旧密钥身份被自动合并 | 迁移表明确旧主体→新个人主体，经总部确认；历史审计记录不重写 |
| R14 | P1 | 审批通过后旧会话保留被撤销能力 | 会话只证明身份，授权从当前成员记录查；撤权/停用立即影响下一次请求 |

## 6. 账号注册、开通与登录

### 6.1 一个正式入口

官网“进入工作区”进入统一登录页，呈现邮箱/用户名、密码、登录、注册账号、忘记密码。页面不显示任何总部/渠道/客户角色选择，不要求输入接入密钥。成功登录后根据当前授权自动进入工作空间。

“查看示例项目”是较弱的次级入口，仅显示隔离、脱敏、只读的虚拟数据；不能匿名打开总部权限。已拥有写权限的内部验收人员使用个人测试账号进入可写演练。

登录页视觉：左侧简短价值说明和一张有明确“示例”标识的工作区预览；右侧简洁登录卡。手机只保留表单和短说明。注册、登录、开通进度使用相同品牌样式，注册页只收完成申请所需资料。

### 6.2 用户旅程

1. **注册账号**：姓名、邮箱、密码；企业名称与网站作为开通申请资料，可先注册后补充。已存在账户走登录/找回，不另造账号。
2. **验证邮箱**：验证前可以登录自己的受限账户页；无企业业务数据访问权。更正邮箱需要重新验证。
3. **申请开通**：选择“申请企业服务”或“申请渠道合作”等业务意图，不选择系统角色。填写必要企业、网站及说明，保存明确申请编号与时间。
4. **总部审核**：核对归属，关联已有组织或建立新组织，再绑定客户/项目和功能范围；需要补充时在账号页显示具体要求。
5. **用户进入工作区**：审批通过无需再输入服务密钥；已有登录会话读取新授权后出现入口。
6. **未通过/暂停**：显示可理解原因、下一步和原申请处理记录；无法访问被撤销企业数据，不删除历史客户资料。

邮件验证与业务开通不是同一状态。建议分别表达账号状态、邮箱状态、开通申请状态、工作空间成员授权，避免一个“已批准”掩盖全部差异。

### 6.3 总部的开通操作

管理员在“运营中心→账号与权限”查看申请队列。详情包含申请资料、已核验信息、推荐匹配企业、当前成员范围和处理记录。匹配已有企业需要主动确认，禁止仅凭同名或邮箱域名自动加入。

操作为：要求补充、关联企业、设定客户/项目、勾选业务能力、开通、拒绝并说明、暂停/恢复。批准界面在提交前显示完整影响范围。并发批准有版本与幂等保护。总部运营可整理资料和受理，不自动获得授权审批能力。

首个总部管理员由受控维护流程建立。禁止公开注册表单自选或自动升级内部身份。首期成员关系由总部管理，不在此轮扩展企业自助邀请、支付或套餐系统。

## 7. 工作界面与信息架构

### 7.1 一套框架，六个日常工作区

顶栏显示产品标识、当前企业/品牌/项目、必要的日期/数据范围、个人账号菜单。只有一个可访问工作空间时默认进入，不增加选择步骤。多企业用户可切换被授权的工作空间，选择器不显示tenant或数据库编号。

常规主导航：**工作台／效果洞察／问题与内容／优化任务／品牌资料／报告中心**。

总部额外有“运营中心”，渠道商有“客户管理”；账号授权入口只给有管理能力者。业务需求与交付放入运营或客户/项目详情，不再保留一套与GEO横向菜单平行的主导航。旧地址保留兼容跳转。

| 原核心功能 | 新位置 | 保留的能力 |
|---|---|---|
| 增长概览 | 工作台 | 当前情况、待我处理、下一步、更新记录 |
| 测量与证据、监控与验证 | 效果洞察 | 测量/复测批次、问题表现、可比性、回答与引用、来源质量 |
| 竞品与SEO | 效果洞察→竞品/搜索表现 | 竞品档案、关键词、排名观测、原SEO诊断规则；与AI回答分开展示 |
| 问题、人群、场景、主题、内容任务 | 问题与内容的二级页 | 维护与对象关联，新增/编辑不在同页展开 |
| 诊断、行动、内容发布 | 优化任务 | 发现→依据→任务→执行反馈→总部复核→发布→复测；内容发布不是报告发布 |
| 品牌、产品、页面、业务事实、实体 | 品牌资料 | 结构化资料、来源、版本与编辑权限 |
| 固定增长报告、历史交付报告 | 报告中心分栏 | 版本、安全快照、撤回、历史阅读与打印，不混并两类报告状态 |

### 7.2 四类身份的首页重点

| 身份 | 首屏回答的问题 | 默认主操作 |
|---|---|---|
| 总部管理员 | 谁待开通、哪些项目受阻、哪项审批需要我决定 | 处理开通/权限申请、查看阻塞原因 |
| 总部运营 | 今天需要处理哪些证据、诊断、内容与复测 | 进入我的专业待办，按具体任务处理 |
| 渠道商管理员 | 我的客户有哪些变化、谁缺资料、哪个需求等待处理 | 打开客户、建档或提交服务需求、协助补充 |
| 客户成员 | 品牌现在怎样、有什么变化、我需要配合什么 | 处理被指派事项、补充资料、阅读最新已发布报告 |

客户端不再分两个入口或显示“客户编辑/查看”大标签。有权限的动作在正确位置出现；无写权限但与任务相关时说明“当前可查看，由服务团队处理”，不显示可点击后才报403的按钮。

### 7.3 客户工作台首屏结构

1. **当前范围与数据时间**：品牌、市场、语言、最近可用数据时间；未采集就明确显示。
2. **当前情况**：最近已复核结果、前后可比对照、重要发现；对象计数下沉到详情。
3. **待我处理**：最多3项紧要任务卡，包含事情、原因、截止/更新时间、直接操作；没有待办显示“当前无需处理”。
4. **下一步建议**：与证据、诊断和行动关联，不凭空生成增长承诺。
5. **最新报告与最近更新**：版本、发布时间、查看入口；详细审计不占据客户首页。

不把两个点包装为连续趋势，不添加没有治理口径的增长分/情绪分/SOV。只有两个可比观测时显示前后对照；时间序列和聚合指标必须满足现有核心定义及来源条件。缺失、未采集、质量待复核、读取失败、零值各自表达。

## 8. 关键任务重新设计

### 8.1 任务详情取代“选对象＋选状态”

从“补充选型资料”卡片进入对应任务，已固定客户、项目、诊断和页面。详情显示：为什么需要处理、支撑证据、需要完成的内容、当前负责人、可执行的下一步、历史反馈。

客户动作按能力/指派/状态显示：开始处理、补充资料、保存当前输入、提交执行说明、请求团队协助。客户不能把行动直接标为已发布、已复测或已验收。

需要新增的反馈记录必须实际持久化，并让总部看到待复核材料、确认或退回补充；其状态属于协作记录，不扩写原Action冻结状态枚举。诊断范围和target_context从可信关联对象带入；普通用户不再手工重复同一目标字符串。

### 8.2 一次只完成一个编辑任务

桌面使用紧凑列表、行内主操作及详情页/侧栏，新增为明确按钮；编辑带入当前值。手机使用摘要卡和独立全屏详情。人群、场景、主题为二级页或关联选择器，不在“问题”页同时展示10个创建/修改表单。

常用表单只展现当前任务相关字段；错误贴近字段并定位，失败保留已填内容。版本冲突提供“核对最新内容”，不能静默覆盖。切换企业/项目、退出前处理未保存内容；不同身份之间不恢复私人输入。

### 8.3 测量登记重设计

客户看到“申请测量/复测”及进度。总部默认使用“选择已采集结果/导入规定格式文件→预览来源与缺项→核验入库”的流程。输入文件有大小/格式/字段白名单，不开放任意服务器路径、SQL或内部采集命令。

技术元数据由可信采集记录带入并可展开查看。没有真实配置摘要、时间或模型版本时显示缺项；不生成假值填满表单，不放宽核心比较要求。导入依然默认HOLD，经总部核验后才可用于结论。

专业手工登记保留为次级方式，按“问题与平台／回答与来源／采集条件／核对提交”分步，每步聚焦少数输入。可推导字段从真实来源取得；不能推导的仍需核实。此功能要与现有采集产物格式联调，不承诺换界面即可自动采集。

### 8.4 状态、结果和错误

- 普通用户看业务含义，不输入内部状态码。按钮只提供服务端允许的下一步。
- 请求失败：留在当前任务并提供重试；登录失效：说明原因并重新认证；无权限：保留安全范围和联系路径；未开通：展示自己的申请进度。
- 来源质量变化：继续执行既有撤销/隐藏规则，界面显示“来源待重新核验”，不称“没有结果”。
- 报告同时显示适用范围、来源时间与限制；打印保留必要数据质量说明，不打印内部授权或技术调试内容。

## 9. 视觉与交互规范

方向：明亮中性背景、清晰的深色文字、蓝色主操作，异常使用有文字说明的状态色。减少全页蓝色卡片、重复说明和过大的垂直留白；一屏先呈现一个最重要任务。

- 桌面建议左侧约224px，顶栏约64px；内容区采用清晰栅格，顶部范围筛选固定在一致位置。
- 正文14—16px，页面标题24—28px；表格行约44—52px；同一级操作尺寸与位置一致。
- 主按钮每个任务面板原则上一个；“导出、设置、更多”降为次级操作。不要用高亮按钮表达无法执行的动作。
- 状态同时提供文字与图形，不仅靠红绿颜色；普通文字对比度目标至少4.5:1；焦点清楚，支持键盘与标签读屏。此为设计目标，不声明已获无障碍认证。
- 390/768/1440均设计：手机将主导航折叠、关键动作贴近任务；复杂数据表在组件内滚动或变为摘要卡，不使整页横向溢出。
- 日期、时区、数字与缺失值一致；技术元数据、数据质量详细解释放在上下文帮助中，必要限制在结果旁保留，不把三段说明长期堆在首页。

结构示意见同目录 `WORKSPACE-EXPERIENCE-REDESIGN-V2-20261020.html`。它是方案展示板，不是已上线登录页；示例数字不是实测结果，也没有真实登录操作。

## 10. 身份与功能实施约束（开发交接）

### 10.1 账号真源与信任边界

复用官网WordPress账号；密码验证和找回继续由账号系统处理，FastAPI/SQLite不再保存另一份用户密码。自定义产品登录界面不要求用户进入wp-admin。

WordPress认证Cookie/REST nonce只在它自己的认证边界生效，不能把一个nonce或浏览器传来的user_id当成FastAPI可信身份。桥接应由已认证的WordPress服务端向门户建立可校验、短时有效且防重放的身份交换，再由门户查当前成员授权。WordPress官方也明确Cookie认证需已登录用户、正确nonce及对应能力。

门户集成密钥保留为服务器之间的调用凭证，不再作为个人身份，不可仅凭集成密钥＋任意用户头声明某人身份；身份交换和权限查询缺一不可。正式环境使用受保护传输，Cookie/来源防护沿用并联调。

### 10.2 最少必要数据关系

需要明确的持久关系：账号主体（账号发行方＋稳定user_id）、组织成员、平台业务身份/能力、客户与项目范围、开通申请及审批事件、权限版本、协作反馈及处理记录。

一人可属于多个组织，多人可属于同一组织；实际读取必须限定已授权客户/项目。内部总部职能与外部成员采用显式范围授权，不从CMS角色或浏览器参数推断。

客户成员只有一类业务身份；权限至少拆为查看、资料维护、问题/建议提交、测量申请、行动准备、受指派行动处理。关键总部动作不能通过“客户可编辑”总开关授予。所有写入继续包含版本、幂等、状态和引用范围校验。

权限开通申请不复用商业ServiceRequest来冒充账号审批。新增最小协调表不复制Client、Project、Diagnosis、Action或测量系统。任务执行说明与总部复核使用协调记录，业务状态仍调用原核心服务。

### 10.3 页面/API能力契约

后端需要提供当前个人、可进入工作空间、当前授权和允许操作；待开通账号仅能读取自己的申请/账号信息。工作台数据应返回来源/更新时间/可用状态和范围，不能用请求失败填零。

任务详情返回安全证据关联和当前允许的操作；“提交执行说明”真实保存，再形成总部待复核队列。账号开通与权限修改均需要持久审批/幂等/版本，撤销立即影响下一次请求。

公开注册、找回密码、开通申请与受保护工作区区分入口，但使用同一套界面与账号。邮件验证和重置需测试成功、失败、过期、重复使用与更正路径，避免“发出邮件”假成功。审计只记录必要主体与事件，不记录密码或令牌。

### 10.4 迁移与兼容

1. 先盘点实际WordPress用户、当前凭据主体、组织、客户和项目映射，不推测同名/相同邮箱就是同一人。
2. 形成受控迁移映射和回滚检查点，经总部确认后迁移新授权；旧审计actor原样保留，不重写历史记录。
3. 演练使用隔离账号/数据库/会话；不在真实WordPress里批量注册虚拟人员，不发送真实验证邮件。可写演练也必须经过测试账号认证。
4. 旧角色启动器不再是用户入口，仅维护环境显式启用。旧URL兼容到新工作区，但不能绕过个人认证或恢复撤销授权。
5. 原增长核心源码与历史数据保护、租户隔离、快照撤销、指标口径、幂等约束继续作为门槛。

|---|---|---|
| 没有公开角色按钮，是否仍可自己申请总部权限？ | 业务意图不赋权；内部身份受控配置，开通按个人和范围授权 | 方案约束已闭合，待负向接口测试 |
| 客户身份合并是否丢掉只读保护？ | 同一UI＋个人能力＋Action指派；不能批准证据/发布/复测 | 方案约束已闭合，保留并扩展现有回归 |

## 12. 实施顺序与验收标准

### 12.1 依赖顺序

1. 冻结账号与成员关系、审批状态及权限矩阵，完成可信账号桥接设计。
2. 先做统一登录/注册/验证/开通进度与总部审批，以及迁移演练；不能先改完皮肤后补身份。
3. 做统一工作区框架、四种首页内容、范围选择和六个主入口，并保持所有GEO能力可达。
4. 做对象详情、直接任务操作、执行反馈与总部复核闭环，再改测量导入/专业分步。
5. 在隔离演练完成账号全流程、采集产物联调、旧路径兼容、视觉与交互走查，之后做独立实现审计及客户任务测试。

每个阶段交付可审查结果；不以注册、表单或后台接口尚未实现的占位按钮冒充完成。不在本轮修改冻结增长计算，也不扩展支付、佣金、公开分享和企业自助团队管理。

### 12.3 体验目标（未来验收目标，不是已测成绩）

- 用户不需要理解角色代码、租户编号、密钥、配置hash或状态枚举即可完成常用任务。
- 客户首次进入后，60秒内能指出“当前数据情况、待我处理、最新报告”位置；每项重点任务从首页至详情原则上不超过3次导航。
- 首轮邀请至少5名不熟悉系统的客户代表，并由总部/渠道人员完成对应任务；跨全部关键任务的无指导完成率目标至少90%，跨客户/越权误操作0。
- 对术语、找不到入口、误把示例当实测、权限被拒绝却无下一步等问题记录并修订；不能仅由开发者顺利点完就判体验通过。

## 13. 本版决策摘要

采用：个人账号统一登录、总部开通、客户身份合并且能力分配、六个任务工作区、角色首页内容差异、直接任务处理、来源可追溯、示例只读与可写测试分离。

保留：既有业务对象、唯一增长核心、质量与比较/归因规则、历史快照、租户/客户隔离、服务器鉴权、幂等和历史保护。

停止作为用户界面：角色按钮登录、密钥登录、同页成组通用增改表单、手选内部状态、以对象数量作为客户首页主要结果、技术字段替代业务任务。

本轮结论是修改方案V2.0及可视化结构示意，不是部署指令；确认后再依据本版生成实施任务与验收安排。
