**审计意见：**

✅ **设计合理** - 字段覆盖完整，符合文档中"Intervention Log"的要求

⚠️ **需要补充：**
1. `outcome` 字段 - 记录实际结果，与预期对比
2. `updated_by` / `updated_at` - 状态变更追踪
3. `metadata` JSONB - 扩展性字段，存储额外数据

**修正后Schema：**

### 2.2 Cost-to-Serve 追踪系统

**原方案：**
```sql
CREATE TABLE customer_cost_tracking (
    id VARCHAR(256) PRIMARY KEY,
    workspace_id VARCHAR(256) NOT NULL,
    month_start DATE NOT NULL,
    month_end DATE NOT NULL,
    expert_minutes NUMERIC(10,2) DEFAULT 0,
    support_minutes NUMERIC(10,2) DEFAULT 0,
    ai_api_cost NUMERIC(12,2) DEFAULT 0,
    infra_cost NUMERIC(12,2) DEFAULT 0,
    exception_count INTEGER DEFAULT 0,
    total_cost_usd NUMERIC(12,2),
    revenue_usd NUMERIC(12,2),
    contribution_margin_usd NUMERIC(12,2),
    created_at TIMESTAMPTZ DEFAULT NOW()
);
```

**审计意见：**

⚠️ **需要重构：**

1. **不要预计算 total_cost / contribution_margin** - 这些数据应该从查询时计算，避免数据不一致
2. **按天/周粒度记录** - 月度聚合会丢失细节，不利于分析
3. **加入事件驱动记录** - 每次专家操作应自动记录时间，而非手动填报

**修正后Schema：**
```sql
-- 事件记录表：每次成本消耗的记录
CREATE TABLE cost_events (
    id VARCHAR(256) PRIMARY KEY,
    workspace_id VARCHAR(256) NOT NULL REFERENCES workspaces(id),
    event_type VARCHAR(64) NOT NULL,  -- 'expert_time', 'support_time', 'api_call', 'infra_usage'
    event_date DATE NOT NULL,
    duration_minutes NUMERIC(10,2) DEFAULT 0,
    cost_usd NUMERIC(12,2) DEFAULT 0,
    description TEXT,
    related_intervention_id VARCHAR(256),  -- 关联到干预日志
    created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_cost_events_workspace ON cost_events(workspace_id, event_date DESC);

-- 月度聚合视图（查询时生成，不存表）
CREATE OR REPLACE VIEW monthly_cost_summary AS
SELECT
    workspace_id,
    DATE_TRUNC('month', event_date) AS month,
    SUM(CASE WHEN event_type = 'expert_time' THEN duration_minutes ELSE 0 END) AS expert_minutes,
    SUM(CASE WHEN event_type = 'support_time' THEN duration_minutes ELSE 0 END) AS support_minutes,
    SUM(cost_usd) AS total_cost_usd,
    COUNT(DISTINCT CASE WHEN event_type = 'api_call' THEN id END) AS api_call_count
FROM cost_events
GROUP BY workspace_id, DATE_TRUNC('month', event_date);
```

**商业逻辑修正：**
- 原始方案要求月度汇总，但实际运营中需要实时追踪
- 改为事件驱动，前端展示时按维度聚合
- `related_intervention_id` 建立与GEO Intervention Log的关联

## 三、关键架构问题

### 3.1 多租户数据隔离

**现状：** 现有系统使用 `organization` + `workspace` 两层结构

**问题：** Partner客户需要在Partner Portal中隔离查看

**解决方案：**
```typescript
// middleware/partnerAccess.ts
export const partnerWorkspaceAccess = t.middleware(async ({ ctx, next }) => {
  const user = ctx.session?.user;
  if (!user) throw new AuthError("Unauthorized");

  const partnerId = ctx.headers.get("x-partner-id");

  if (!partnerId) {
    // 非Partner用户，走原有workspace验证
    return next({ ctx });
  }

  // Partner用户只能访问自己关联的workspace
  const partnerCustomer = await ctx.db.query.partnerCustomers.findFirst({
    where: (pc, { and, eq }) =>
      and(eq(pc.partnerId, partnerId), eq(pc.workspaceId, ctx.workspaceId))
  });

  if (!partnerCustomer) {
    throw new AuthError("Access denied to this workspace");
  }

  return next({
    ctx: { ...ctx, partnerId, partnerCustomer }
  });
});
```
